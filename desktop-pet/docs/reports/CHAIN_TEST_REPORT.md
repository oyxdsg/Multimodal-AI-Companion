## 〇、状态接地复测（最新 · 权威）

> 上一版测试只看「NLU 轨迹 + `ok=True` 回执 + AI 说了什么」就判执行——这是错的：回执只代表
> 「指令被接受」，不代表游戏里真的发生了。本版升级为**状态接地 + 前置门控**：
>
> 1. **前置门控**：每条指令先读女仆全量感知，确认目标真实存在才发（有猪才打、地上有掉落才捡、主手有东西才收）；
> 2. **状态回读验证**：指令后再次读全量感知，用 `task / mainhand / inventory / ai_busy` 这几个
>    **指令真正驱动的字段**的 diff 判执行——位置/朝向/周边实体/心跳每帧都在变，不算证据。

### 复测结果（2026-09-12 23:09 – 23:13，9 条状态门控用例）

| # | 指令 | 状态实锤 | 结论 |
|---|---|---|---|

| S4 | 把钻石丢给我 | `钻石 61 → 60` | ✅ 真实丢出（NLU drop 0.99 自动执行，丢到主人脚边） |

「置信度不足未执行」——**判定不再信 AI 的话，全凭游戏状态变化**。

### 本轮顺带修掉的 4 个 harness 缺陷（都在真机里暴露）

1. 状态转储用**文件大小**判更新 → 女仆死后快照冻结、大小不变，永远读不到 → 改 **mtime**；
2. `nearby`/`inventory` 结构解析错（nearby 是 `{hostiles/animals/players/items}`、inventory 是 `{slots:[…]}`）；
3. **重召后 `state()` 取到已死的旧女仆**（旧 uuid 快照冻结在 health=0）→ 改优先返回活女仆；
4. 判定字段过宽（把 `nearby` 也算行为变化，史莱姆自己走动就误报「已执行」）→ 收窄到 task/mainhand/inventory/ai_busy。

### 一个方法论级发现

复测前女仆**死于一只末影人**（指令前状态已 17.42 血、1 格外有末影人）。旧方法会继续报「执行成功」，
状态一看就是死了。→ **状态接地是必要的，且测试前必须确认场景安全（无敌对怪、女仆满血）**。

## 四、根因定位

### R1（严重·我引入的回归）`transfer` 对抗样本污染了 `equip`

**现象**：T13「换上新打的铁镐」→ `transfer 0.47`，合并前是 `equip 0.91`。

**A/B 证据**（同一批句子，合并前后两个模型）：

| 短语 | 合并前 | 当前 |
|---|---|---|
| 换上新打的铁镐 | equip 0.91 | **transfer 0.47** |
| 把铁镐换到手上 | equip 0.77 | **transfer 0.98** |
| 拿出钻石剑 | drop 0.34 | ✅ equip 0.81 |
| 装备铁镐 | equip 0.98 | equip 0.99 |
| 换上镐子 | equip 1.00 | equip 1.00 |

**根因**：本轮我给 `transfer` 补的对抗样本里有 **`把铁镐收进背包`**，把「铁镐」这个高频 `equip` 宾语塞进了 `transfer` 的分布；而 `equip` 的模板是「换上{item}」，`{item}` 词表里没有「铁镐」。于是「换…镐」被整体拉向 `transfer`。

**修法（很小）**：把那行样本换成中性物品，或反过来给 `equip` 补「换上铁镐 / 把铁镐换到手上 / 切出铁镐」——让**动词与槽位**决定边界，而不是靠物品名。

### R2（严重）「X子」后缀的拼音匹配不上官方物品名

**现象**：T05「帮我合成一把稿子」→ `craft 0.99` 正确，但 `未执行原因：没听出要合成哪个物品`。

**反证「词典是好的」**：同一会话 22:25:21 的 T06「把钻石剑丢给我」成功解析出 `minecraft:diamond_sword` → 物品索引可用；22:24:08 也确认收到 **1516 条**物品索引。

**离线复现**（`slots.ItemIndex.resolve`）：

| 词典 | 「帮我合成一把稿子」 | 「合成一把铁镐」 |
|---|---|---|
| 官方名（木镐/铁镐…，**无「镐子」条目**） | ❌ 无候选 | ✅ 铁镐 (exact) |
| 含「镐子」条目（= `tests/test_nlu.py` 里的假词典） | ✅ 镐子 (pinyin 0.95) | ✅ 铁镐 |

**根因**：「镐子」带了个「子」字，拼音全词（`gaozi`）匹配不上官方名「木镐」（`mugao`）；而单测里用的假词典恰好有「镐子」这一条，所以**一直是绿的**——测试装置比现实善良。

**修法**：拼音匹配把「子/儿/头」这类**口语后缀**当可省尾字（或在建索引时给每个物品名额外注册一版去后缀别名）。

### R3（中）`store` ↔ `collect` 双双摊薄到阈值以下

「把东西都收起来」→ `store 0.50` / `collect 0.48`；「把散落的东西收纳一下」→ `collect 0.59` / `store 0.37`。

**A/B 对比**「把东西都收起来」：合并前 `collect 0.92`（**意图是错的，但会自信地误执行一次 collect**）→ 现在 `store 0.50`（意图对了，但低于 0.55 什么都不做）。

**判断**：这其实是**变好了**——从「错误动作」变成「安全不动」，但离「正确动作」还差一截。规范（§11.1）已经写明「收拾/收纳动词 → store」，语料还需要更多「收纳 vs 捡地上的」对照来把 margin 拉开。

### R4（中）阈值与意图错判

* **T04**「打死旁边那头猪」：意图、目标（`minecraft:pig`）都对，但 **0.78 < AUTO 0.85** → 不执行。用户说这句话是真想让它动手的，这是**产品体验缺口**。
* **T08**「跟紧我，别走丢」→ `drop 0.60`（应 move/guard）：明显错判，且因为 `<0.55` 的邻居太多，属于模型覆盖不足。
* **T09**「守着这儿别让怪靠近」→ `move 0.70`（次选 `guard 0.22`）：按 §11.1 规范「守/护/挡 → guard」，这里判成 move，规范没学会。

### R5（认知纠正）「AI 疯狂发无效 DSL」多半是**测试噪声**，不是 AI 行为

项目的待办里长期挂着一条高优先级问题：「`crash.log` 有 57 组 `MaidIntentParseError`（`move` 坐标错 / 未知指令 `fly` / 缺 `pos`）→ AI 参数质量差」。**本次实测推翻了它的大部分：**

| 证据 | 内容 |
|---|---|
| `crash.log` 全量统计（72 组） | `未知指令: fly` **24 次** · `缺少参数 [move]: pos` **24 次** · `坐标格式错误 [1,2]` **22 次** · `未知指令: cmd` 2 次 |
| 与测试夹具逐字对照 | `tests/test_maid_loop.py` 里正有 `parse("【fly()】你好")`、`parse("【move(pos=[1,2])】")`、`parse("【move()】")` —— **完全对应** |
| 本轮 14 条真机对话 | `crash.log` **新增 0 组**（这是唯一一次「AI 真的在说话」的采样） |

**结论**：那 72 组里 **70 组是跑单元测试刷出来的**（每跑一次 `test_maid_loop.py` 加 3 组），
只有 2 组 `未知指令: cmd` 是真实的（= 2.19.1 已修的 prompt 占位符问题）。

> **2.20.0 追加证据**（`API_PROMPT_TEST_REPORT.md`）：另跑了 18 条真实 API 对话 + 6 条游戏模式专项，
> AI 主动发出的指令（`attack` / `guard` / `build` / `mine`）**参数 100% 合规**，零 `MaidIntentParseError`。
> 这条待办可以**彻底关闭**。

**顺带发现一个卫生问题**：`tests/test_maid_loop.py` 会把「故意构造的坏指令」写进**生产日志** `logs/crash.log`，
让人误判真实故障率——建议测试时把 DSL 错误日志重定向到临时文件（或给解析器加一个日志目标参数）。

## 五、本轮 2.19.2 改动的真实效果（诚实版）


上轮我用 208 条人工测试集得出「88.46%，比上版 87.5% 略好，但差值在噪声内」。**这次真机测试给出了更有信息量的结论**：

| 维度 | 结论 |
|---|---|
| 合并 `collect`/`pickup` | ✅ 真的有效（T02/T14 稳定；探针 16 条里 12/16 → 13/16） |
| `equip` 边界 | ❌ **被我的 transfer 样本带偏**（R1），这是实打实的回归 |
| `store` 边界 | ⚠️ 标签修正了，但置信度被摊薄（R3） |
| 整体风险 | 208 条人工测试集**没能**覆盖这些真实口吻——它太干净了 |

> 教训：**人工测试集只有 208 条，且措辞偏「教材式」**。像「换上新打的铁镐」「把散落的东西收纳一下」这种真人口吻没进测试集，所以上轮的「提升」结论偏乐观。真机测试应当成为回归验收的一部分。

## 六、其他观察

1. **AI 反而比 NLU 更懂**：T05 里 AI 主动说「稿子？镐子吧！你要啥材质的」——大 AI 猜对了，是本地词典没兜住。T04 里 AI 说「你确定旁边真有猪吗」——AI 不知道附近有没有猪，因为 `[态]` 里没有周边实体清单。
2. **TTS 严重积压**：连发 14 条（每条约 7s）时，语音队列从 0 涨到 **36.9 秒积压**（单条合成 4–14s）。**不阻塞聊天**（AI 回复照常），但用户体验上是「说了半天话还在念前面的」。
3. **AI 指令（DSL）路径本次未被真正验证**：B 组三条（T07/T08/T09）里，T07 被本地 NLU 抢先执行了（按设计抑制 AI 指令）；T08/T09 置信度落在 HINT 档，AI 收到提示后也**没有**发指令。所以「AI 主动发 `【attack】`」这条路径这次没跑到——需要另设计用例（例如带坐标的 `mine/move`，本地 NLU 不会自动执行）。
4. `logs/perf.log` 与 `logs/crash.log` 是 **UTF-8**（不是 GBK），且含少量非法字节（严格 UTF-8 解码会失败），读取需 `errors="replace"`。这条值得写进踩坑记录——我一开始按 GBK 读，整段都是乱码。
