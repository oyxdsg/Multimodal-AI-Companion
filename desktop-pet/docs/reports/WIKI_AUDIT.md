## 一、链路全景

Wiki 能力**只挂在游戏模式**（收到 MC 事件时给回复注入背景知识），聊天/语音链路不触发。

```
模组事件窗口 (deskpet/*.jsonl)
   │  game_handler._extract_win_targets()   ← 从 highlights 取中文实体名（主力）
   │  + mc_log.extract_terms()               ← 固定词表兜底（约 20 英文 + 32 中文）
   ▼
game/processor.process_game(events, terms, player)
   │
   ├─ ① 实体提取补全   wiki_kb.match_terms(log_text)
   │                   ← 词表 = common 标题 + **重定向别名**；n-gram 滑窗；单字需上下文
   ├─ ② 低频过滤       wiki_kb.is_worth_wiki(term)        ← lowfreq 才走，过滤白名单 + common 基础实体，保留 rare + 较新版本内容
   ├─ ③ 会话内去重     self._wiki_done（绑 ai_session_id，换会话重置）
   │                   ← 只记「真正产出过知识」的词，空结果下一轮重试
   └─ ④ 三层知识链路   GameProcessor._wiki_knowledge() → (文本, 命中词)
        │
        ├─ L1 curated   nlu/wiki_refine/curated.py :: prompt([term])   1490 条人工库
        │                 └ **精确匹配**（name / id / aliases）命中 →【名称】+ facts + 趣闻
        ├─ L2 精炼模型  wiki_kb.search_candidates() → nlu/wiki_refine/refine.py
        │                 └ 3 分类打分（know/fun/drop）→【要点】+【趣闻】，≤ MAX_TOTAL(172)
        └─ L3 原文兜底  wiki_kb.search_text()  规则摘要（_snippet，≤180 字）
        ▼
  注入 GAME_PROMPT 的 {wiki} 槽位 → 主对话大 AI
```

**开关**：`WIKI_REFINE_ENGINE = local`（默认）/ `ai`（旧的大 AI 提炼会话）/ `off`。
UI 在「聊天 ⚙ 设置 → 基础」。

### 1.1 输出语义：是「互斥兜底链」，**不是三层叠加**

三层**不会同时全部输出**。真实语义是「L1 逐词命中 → 未命中的词再走 L2，L2 无结果才用 L3」：

| | L1 curated | L2 精炼模型 | L3 原文兜底 |
|---|---|---|---|
| 粒度 | **逐词**（每个词命中就追加一块 `【名称】…`） | **批量**（全部漏网词合并成一次调用） | **批量**（同 L2 的输入） |
| 触发 | 词有精确条目 | L1 漏网的词 | **L2 返回空**时替换 L2 |
| 与相邻层关系 | 可与 L2 / L3 共存 | 与 L3 **互斥** | 与 L2 互斥 |

所以实际组合只有这几种：**只 L1**（全部命中）/ **只 L2** / **只 L3** / **L1 + L2** / **L1 + L3**。
`off` 档完全跳过 L1，只用 L3；`ai` 档是 L1 + 大 AI 提炼会话（提炼返回「无」才用原文）。

**实测注入体量**（`_wiki_knowledge` 直接调用；2.21.0 已加总额预算 `GAME_WIKI_MAX_CHARS = 480`）：

| 场景 | 加预算前 | 加预算后 |
|---|---|---|
| 1 词命中 L1 | 165 字 | 165 字 |
| 3 词命中 L1 | 383 字 | 383 字 |
| 12 词全命中 L1（模组 highlights 上限） | **1460 字** | **468 字** |
| 6 词全走 L2 | 128 字 | 376 字（覆盖实体 2 → 6） |
| L3 原文（`GAME_WIKI_LIMIT = 2`） | 80~92 字 | 80~92 字 |

## 三、修复前 → 修复后（同一工具复测）

### 3.1 P0-1 实体提取：最常用的实体拿不到

MC 中文 Wiki 的**材质工具/装备没有独立页面**，只有单字总览页，变体只作重定向别名
（铁镐→「镐」、钻石剑→「剑」、樱花木→「木头」）。旧 `match_terms` 只对 common 标题做
逐条 `t in text` 字面扫描、**不查别名**。

| 事件行 | 修复前 | 修复后 |
|---|---|---|
| `[获得] 铁镐 x1` | `[]` | **`['铁镐']`** |
| `[获得] 木镐 x1` | `[]` | **`['木镐']`** |
| `[获得] 钻石剑 x1` | `['钻石']`（降级成子串，语义错） | **`['钻石剑']`** |
| `[获得] 樱花木 x8` | `[]` | **`['樱花木']`** |
| `[击杀] 猪 x1` | `[]`（42 个单字标题被 `len>=2` 排除） | **`['猪']`** |
| `[获得] 橡木原木 x3` | `['原木']` | **`['橡木原木']`** |
| `[击杀] 苦力怕 x2` | `['苦力怕']` ✅ | `['苦力怕']` ✅ |
| `[破坏] 钻石矿石 x5` | `['钻石矿石']` ✅ | `['钻石矿石']` ✅ |
| 今天天气怎么样呀 | `[]` ✅ | `[]` ✅ |
| 我去水边看看风景 | — | `[]` ✅（单字守卫生效，「水」不误命中） |
| 耗时 | 0.7 ms | **0.5 ms** |

单字实体守卫：`[击杀] 猪 x1` 认（有事件动词/数量标记），闲聊里的单字不认。

### 3.2 P0-2 curated 抢答

旧 `find()` = 「双向子串 + 字典顺序首命中」，查不到就顶答：

| 查询 | 修复前 | 修复后 |
|---|---|---|

| 嗅探兽 | 进度条目`【小小嗅探兽】`（错，且是进度页） | **未命中** → L2/L3 兜底 |
| 木板 | `【金合欢木板】` | **未命中** → L2/L3 兜底 |
| 铁镐 / 钻石剑 / 钻石镐 / 僵尸 / 铁傀儡 / 铜灯 / 试炼密室 | ✅ 正确 | ✅ 仍正确 |
| `prompt()` 耗时 | 0.167 ms | **0.022 ms** |

代价：对本地库 common 标题的覆盖率 55.8% → **17.3%**。这个数字**不代表能力下降**——
旧数字里的差集大部分是"错答"；且真实入口是模组报的物品名（铁镐/钻石剑…），
它们在 `pages` 里根本不是标题、只是重定向，按标题统计天然低估。

### 3.3 P1-2 分类噪音

| 类别 | 修复前 | 修复后 |
|---|---|---|
| common | 4382 | **3539**（−843） |
| version | 2030 | 2728 |
| tech | 338 | 444 |
| rare | 765 | 804 |
| common 里疑似非实体 | ~199 | **148** |

规则：版本前缀（`Java版/基岩版/携带版/教育版/中国版/原主机版` 开头 → 78 条实测零误伤）、
`Java版Alpha v1.0.1` 这类漏判补进 `_VERSION_RE`、正文特征识别音乐曲目/开发方人员/平台版本页、
数据格式页 → tech。真实游戏实体（铁镐/僵尸/苦力怕/音乐唱片/试炼密室…）**零误伤**。

### 3.4 P1-3 精炼预算

| 项 | 修复前 | 修复后 |
|---|---|---|
| 超预算句 | **整句丢弃**（`continue`）→ 长引言可达 100+ 字，一条就把要点挤空 | **截断**到剩余预算 |
| 空要点兜底 | 塞 `rows[0]` 首句，**无长度上限**（实测比原文还长） | 受 `MAX_TOTAL` 约束 |
| 相似句 | 不去重（「该区域有13张贴纸/12张贴纸」都进） | 字符 Jaccard ≥ 0.7 跳过 |
| 预算 | KNOW 140 / FUN 60 | KNOW 120 / FUN 40，`MAX_TOTAL` = **172** ≤ 单页原文上限 180 |
| 实测输出 | 均值 124 字（最长 214） | **均值 129 字，区间 114~162，全部 ≤ 172** |

用模组真会报的实体名探测（`猪/牛/木板/樱花木/嗅探兽/橡木原木/床`），精炼输出内容质量正常
（如「猪」→ 引言 + 繁殖 + 掉落来源）。

> 说明：单页对比下 refine 仍可能比 `search_text` 的 `_snippet` 更长——因为 `_snippet`
> 对短页常只能给 40~90 字（锚点命中过短时回退小节提取）。这里守的是**硬上限**
> （172 < 180），而 refine 的收益是**相关性**（从整页候选句里选引言/配方/警告句）。
> 另：改前 refine 兜底路径的最长输出 214 字，已超单页上限，属真实回退。

### 3.5 P2 死代码与去重策略

- 删除 `mc_log.wiki_search` / `_wiki_fetch` / `_WIKI_API` / `_WIKI_CACHE` / `_WIKI_LOCK` /
  `_WIKI_SESSION` / `_WIKI_EXTRACT_MAX` 及仅供其用的 `threading` / `time` / `urllib.parse`
  导入（全项目零调用）；`extract_terms` 的兜底词表保留。
- 去重记账改为**只记产出过知识的词**：旧实现「无论命中与否都记录」，
  某次因库状态没查到就整局不再尝试（只能换会话重置）。

### 3.6 注入总额预算（2.21.0 补充）

L1 是**逐词**产出块的，而模组 highlights 最多给 12 个词 → 12 个词全命中就是 **1460 字**。
`GAME_WIKI_LIMIT = 2` 只约束 L2/L3 的**页数**，管不到 L1，所以此前整条 `{wiki}` 注入没有总额约束。

- 新增 `config.GAME_WIKI_MAX_CHARS = 480`：`_clip_knowledge()` 按
  「L1 命中块（按模组给的顺序，具体词条优先）→ L2/L3 兜底块」贪心塞入，超预算截断。
- 块之间的换行也计入预算，保证总长有**硬上界**（不会因分隔符溢出）。
- 截断优先收在换行/句读边界（共用 `nlu.wiki_refine.refine.cut_at_boundary`），避免注入半句话。
- 实测：12 词全命中 **1460 → 468 字**（6 块）；单物品/3 物品不受影响（165 / 383 字）。

### 3.7 L2 逐实体分组（2.21.0 补充）

`search_candidates(terms, limit)` 的 limit 是**跨词共享**的页数上限 → 6 个词只取到 2 页。

- 新增 `per_term` 参数：精炼路径改为**逐词各取 1 页**，并给每行打上 `term` / `title`；
  **同一页面不会被两个词重复取用**（避免同族词重复注入，如铁镐/钻石镐都指向「镐」页）。
- `refine.refine()` 见到 `term` 就**按实体分组**分别选句，每块加 `【实体名】` 前缀。
  不分组会跨实体混排 —— 实测「猪」的段落后面直接接上「它们是皮革、生牛肉、牛排和奶桶的
  主要来源」（那句讲的是**牛**）。
- 实测：覆盖实体 **2 → 6**；成本 `search_candidates + refine` 76ms → **168ms/次**
  （候选 135 行；纯本地 numpy 前向，在工作线程，不影响 UI）。

另外修掉一处「填满剩余额度」的副作用：精炼在剩余预算不足以放下一整句时，改为**跳过该句、
给后面的短句机会**，而不是把句子切碎塞进去（实测会注入到「…无法被喂食除金」这种碎片）。
「什么都没选上」的情况仍由兜底分支保证至少有一条内容。
