# API 后端多模式实测报告

> 被测版本：`config.VERSION = 2.20.0`（按后端分离 prompt）
> 后端：`deepseek-api`（官方 API，MessagesBackend + 精简人设）
> 模型：`deepseek-chat`　测试方式：真实调用 API，不走 UI、不动鼠标键盘
> 测试时间：2026-09-14

---

## 一、链路正确性（结构化断言）

| 检查项 | 结果 |
|---|---|
| 走的人设文件 | 女仆 → `prompt_api.txt`；御坂 → `prompt2_api.txt`　✅ |
| system 每轮重发且含【当前模式】 | 9/9 条 ✅ |
| system 含「女仆指令」章节（AI-DSL 闭环前提） | 9/9 条 ✅ |
| **user 消息不含「现在切换到 x、模式名」**（本轮核心目标） | 9/9 条 ✅ |
| system 长度 | 7331 ~ 7566 字（全长版 6923/7078 + 模式段，比原方案每轮省约 43%） |

## 二、模式切换是否生效（AI 实际表现）

| 模式 | 表现 | 结论 |
|---|---|---|
| 1 日常 | 情感共鸣、撒娇、白饭梗（"这下得请我吃白饭了吧"） | ✅ 人设生效 |
| 2 工作 | 严格一句话、以"悄悄告诉你/你知道吗"起句、无动作标签 | ✅ 与日常明显区别 |
| 3 游戏 | 读【态】做战术建议、发【指令】指挥女仆 | ✅ 模式段生效 |

**模式干扰检查**：工作模式下 AI 没有把日常人设的撒娇语气带进去，说明 system 里的模式段确实在压人设。

## 三、游戏模式专项（最有价值的部分）

### AI-DSL 闭环在 API 后端下**确实活着**

AI 主动发出了这些指令（全部通过 `maid_intent.parse` 校验、参数合法）：

| 人设 | AI 原文（节选） | 解析结果 |
|---|---|---|
| 女仆 | `…你赶紧垫高两格…{思考}【attack(range=10)】` | `attack range=10` ✅ |
| 女仆 | `…我这就给你圈块地打地基{开心}【build(pos=~, height=3)】` | `build pos=~ height=3` ✅ |
| 女仆 | `…天亮给你搭个大house！{挥手}【mine(pos=[128,42,-315], range=4, count=8)】` | 坐标三整数 ✅ |
| 御坂 | `…先清掉！【attack(range=10, target=minecraft:zombie)】` | `target` 用英文实体 id ✅ |
| 御坂 | `…你赶紧垫方块往上爬！{兴奋}【guard(range=10)】` | `guard range=10` ✅ |

**瞬态状态利用率**：AI 主动引用了 `[态]` 里的信息 ——
- "你身后有两只僵尸在蹭呢" / "这位置离僵尸才8格" / "先抄家伙打啊"
- 第3条甚至直接拿 `pos=(128,42,-315)` 生成了绝对坐标 `mine` 指令

### 输出顺序与标签格式（`probe_dsl_order.py` 验证）

指令写在 `{动作}` 之前时，解析器**位置无关**，`{动作}` 标签会被完整保留 —— 功能不出错。

## 四、本轮实测发现并修掉的 3 个精简版缺陷

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 御坂版动作标签输出 `[坐下]` `[开心]`（方括号） | 精简时漏了「必须用 `{}` 包裹」的硬约束句（原版 `prompt2.txt` 也缺） | 两份都补「必须用{}包裹（不是[]、不是()）」+ 明确示例 |
| 2 | 御坂版 2/3 条**完全不带**动作标签 | 「每条回复必须带一个{}」的强制语气被压缩掉了 | 两份都补「**每条回复都必须带上一个{动作}，不得省略**（这是在驱动桌宠动画）」 |
| 3 | 女仆版输出 `【指令名(attack(range=10))】` —— 把占位符「指令名」照抄了 | 精简时保留了规范但没给反例（原版有"不要写【cmd(...)】"这类反例） | 两份都补「『指令名』只是格式占位符，**不要照抄**」+ 正误对照 |

### 修复前后对比

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 御坂版带动作标签 | 0 / 3 | 2 / 3 |
| 御坂版答非所问（造房子→说打僵尸） | 1 / 3 | 0 / 3 |
| 女仆版「指令名」照抄 | 1 / 3 | 0 / 3 |
| 指令顺序违规（动作在指令后） | 2 / 6 | 0 / 6 |
| 动作词用方括号 | 3 / 6 | 0 / 6 |

## 五、精修轮（2.20.0 定稿）：女仆指令全域化 + 模式差异

上一轮修完 3 个缺陷后，实测又暴露了 3 个**结构性**问题，本轮一并解决：

| # | 问题 | 根因 | 修法 |
|---|---|---|---|
| 4 | 「女仆指令」写成**游戏模式限定**（"在游戏模式（或你感知到女仆在场）时"），AI 在非游戏模式下不敢发指令 | 精简时把语境条件原样搬了过来，但 MessagesBackend 的 `[态]`/`[系统]` 在**所有模式**都会注入，条件写窄了 | 改标题为「女仆指令（全域可用，不限游戏模式）」，并明确"日常/工作/游戏模式都适用"，列出「感知到女仆在场」的判定口径 |
| 5 | 全文**没有跨模式的指令范例**，AI 不知道非游戏模式该怎么用 | 精简版只留了规则、删了示例 | 新增「女仆指令范例」7 条，覆盖日常/工作/游戏三模式 |
| 6 | 三模式**共用同一套输出格式规则**，但没人告诉 AI"模式只改说什么、不改怎么写"，工作模式容易漏 `{动作}` | 模式段（`config.AI_MODES`）里写着"不输出动作标签"，与人设的"每条必须带 `{动作}`"直接冲突 | 人设新增「模式差异」段，明确三模式共用格式硬规则、`{动作}` 一律必带 |

### 精修后实测（2 人设 × 3 模式 × 3 条 = 18 条，真实 API）

| 指标 | 精修前 | 精修后 |
|---|---|---|
| 带 `{动作}` 标签 | 14 / 18 | **18 / 18** |
| 动作词写 `[]` 方括号 | 3 / 18 | **0 / 18** |
| 工作模式夹带人设梗（撒娇/甜食） | 有 | **0 / 9** |
| 游戏模式主动发指令 | 3 / 6 | **6 / 6** |
| 指令顺序违规 | 2 / 6 | **0 / 6** |
| 指令参数违规 | 0 | **0** |

游戏模式专项结构化校验（`tools/test_api_game.py`）**6/6 全过**：动作标签格式合规、
指令位置在 `{动作}` 之后、参数全部通过 `maid_intent.parse` 校验
（`attack(range=10)` / `guard(range=10)` / `build(pos=~, height=3)`）。

### 顺手修掉的一个真 bug（代码侧）

`config.get_api_prompt()` 原先写的是 `load_system_prompt(persona, pet_name, backend=None)`，
而 `backend=None` 走的是**自动探测当前后端**。这意味着「API 专用提示词」会不会取精简版，
取决于"此刻恰好连着哪个后端" —— 离线生成 / 测试时探测不到 API 后端，就会**错误地拿到全长人设**
（量 token 时表现为"精简版比全长版还长"）。已给 `load_system_prompt` 增加 `backend=True`
（强制精简）分支，`get_api_prompt` 恒用它。回归用例 `[U1d]` 钉住。

### token 成本（每轮 system）

| 人设 | 网页全长版 | API 精简版（精修后） | 省 |
|---|---|---|---|
| 女仆 | 6923 字 | 4587 字（三模式均值） | **34%** |
| 御坂 | 7078 字 | 5235 字（三模式均值） | **26%** |

## 八、结论

1. **按后端分离 prompt 的目标达成**：API 侧 system 带精简人设 + 当前模式，user 消息纯净。
2. **女仆指令章节必须保留是对的** —— 精修后游戏模式 **6/6** 主动发指令，参数完全合规
   （包括 `target=minecraft:zombie`、坐标三整数、`pos=~`）。
3. **精简的副作用是「约束语气被削弱」** —— 这是两轮实测最值得记的教训：
   压缩人设时，**功能性硬约束（动作标签格式 / 必须输出 / 反例 / 模式差异）的措辞不能跟着减**，
   否则模型会漏掉。本轮把这些**全部补回**，并加了回归用例钉死。
4. **「游戏模式限定」是个隐蔽的语义错误** —— 条件写窄会让 AI 在非游戏模式下不敢发指令。
   正确口径是"感知到女仆在场（有 `[态]`/`[系统]` 注入）"，而这在三个模式里都会发生。
5. 精修后 18/18 条都带 `{动作}`、0 条用 `[]`，此前"御坂约 1/3 漏标签"的瑕疵已消失
   （不再需要代码侧兜底标签；如后续多轮验证仍有偶发，再考虑加）。
