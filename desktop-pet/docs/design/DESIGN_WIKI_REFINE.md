# Wiki 精炼与知识库（本地化注入）

> 状态：**已实施**
> 目标：把「Minecraft Wiki 知识注入 AI 对话」从 **大 AI 独立会话提炼** 改为 **本地三层链路**——
> ① 人工提炼的 curated 知识库（1490 条）优先命中 → ② 本地精炼小模型（候选句打分选句）兜底长尾 →
> ③ 原文 / 大 AI 会话保底。省 token、零延迟、离线可用。

---

## 一、为什么做本地化

原链路（`processor.py`）：`wiki_kb.search_text()` 规则摘要 → **新开 DeepSeek 独立会话提炼**（`ai.client.refine_wiki`）→ 注入主对话。

问题：
1. 每次知识查询都调用大 AI（token + 秒级延迟），高频场景成本高
2. 规则摘要（`_snippet` 180 字）信息已压缩，提炼空间小
3. **数据源噪音**：wiki 原文混着数据表/模板残骸/彩蛋垃圾，且高价值知识分散
   （例：「铁镐能挖钻石矿」写在钻石矿石页，不在镐页）

因此拆成三层，各用最合适的工具：

| 层 | 方案 | 理由 |
|---|---|---|
| **高频实体** | **人工提炼 curated 库**（1490 条） | 玩家 95%+ 的问题都是高频实体；人工库质量可控、直接命中 |
| **长尾** | **本地精炼小模型**（3 类打分） | 覆盖 curated 未收录的冷门页，离线毫秒级 |
| **保底** | 原文直注入 / 大 AI 会话 | 任何环节异常/未命中都安全降级，绝不比现状差 |

---

## 二、总体数据流

```
游戏事件 → 提取实体（wiki_kb.match_terms）→ 三层知识链路（_wiki_knowledge）
        │
        ▼
┌─ local（默认，config.WIKI_REFINE_ENGINE）─────────────────────────┐
│ ① curated 命中（1490 条）→ 直接注入【要点】+【趣闻】              │
│ ② 未命中 → 本地精炼模型：search_candidates() 取候选句 → 打分选句  │
│ ③ 仍无结果 → search_text() 原文直注入                            │
└──────────────────────────────────────────────────────────────────┘
        │  ai 档：① 后走大 AI 提炼会话（旧行为）；off 档：完全原文
        ▼
注入 GAME_PROMPT 的 {wiki} 槽位 → 主对话大 AI
```

**关键取舍**：curated 是「人工事实」，精炼模型是「长尾兜底」，大 AI 是「最后保底」——
本地链路尽量自己解决，解决不了才花钱（大 AI）。

## 三、Curated 知识库（1490 条）

### 3.1 覆盖与文件

| 类别 | 条数 | 说明 |
|---|---|---|
| 游戏实体（T1 304 + T2 934） | 1238 | 生物/方块/工具/矿石/食物/药水/附魔/机制/结构/生物群系/村民职业/FAQ/指南/技巧 |
| **成就**（基岩版） | 136 | 中文名映射 + 要求 + 分值 |
| **进度**（Java 版） | 116 | 中文名 + 描述 + 要求 + 上游 |

文件（**单独存放，原 wiki `wiki_data/mcwiki.db` 零改动**）：
```
nlu/wiki_refine/data/
  curated_all.jsonl           ← 合并总库（1490 条，build_curated.py 生成）
  curated.jsonl / curated_tools / _mobs / _blocks / _food_mech
  / _extra1..3 / _t2_b1..49   ← 分片（按批可编辑）
  curated_advancements.jsonl  ← 进度（自动提取）
  curated_achievements.jsonl  ← 成就（中文名映射）
```

### 3.2 条目格式（按预期分类）

```json
{"id":"iron_pickaxe","name":"铁镐","category":"工具/采集",
 "summary":"铁镐是中期主力挖掘工具，能开采钻石矿、金矿、红石…",
 "facts":[{"type":"配方","text":"3个铁锭 + 2根木棍，工作台合成"},
          {"type":"能力","text":"可挖掘钻石矿石、金矿石、红石矿石…"},
          {"type":"耐久","text":"耐久251，可用铁锭修复"}],
 "fun":"大部分玩家第一次见到钻石，就是靠铁镐挖出来的。"}
```

`summary`（一句话定义）+ `facts[type]`（分类事实）+ `fun`（可选趣闻，给 AI 当聊天素材）。

### 3.3 生成与校验

* **游戏实体**：人工提炼（AI 草稿 + 审核），分片批次写入
* **进度**：`gen_advancements.py` 从 wiki「进度」页自动提取（中文名+描述+要求+上游）
* **成就**：`gen_achievements.py` 从 wiki「成就」页提取 + 英文 id→中文名映射
* **合并/校验**：`build_curated.py`（必需字段、id 唯一、JSON 合法）
* **覆盖审计**：对比 wiki 页面标题，输出「已覆盖 / 未覆盖（周边页 / 实体缺口）」报告

## 四、精炼小模型（长尾兜底）

### 4.1 任务定义
把候选句按 **知识 / 趣味 / 丢弃** 三分类打分，精炼时选知识 top-k + 趣闻 1~2 条拼装。
（吸取教训：早期把彩蛋当纯噪音，后修正为「彩蛋是对话乐趣」，单列 `fun` 类。）

### 4.2 数据管线（`nlu/wiki_refine/`）

| 模块 | 作用 |
|---|---|
| `segment.py` | wiki 页面 → 候选句（小节链切分 + junk 检测） |
| `weak_labels.py` | 三分类弱标签（引言/配方→know，彩蛋→fun，数据表/残骸→drop） |
| `build_data.py` | 全量生成训练数据（`seed.jsonl`，10 万+ 句） |
| `curate.py` | 大模型精选校准（修正弱标签错误，`curated.jsonl`） |

### 4.3 模型（`model.py` + `features.py`）

* 架构：字符 1/2/3-gram EmbeddingBag + **结构化特征**（小节类型/配方/引言/位置）→ 64 隐层 → 3 类
* 纯 numpy（训练/推理同代码），体积 **2.16 MB**
* fun 过采样 ×10 缓解类别不平衡（fun 仅 ~2.4%）

### 4.4 指标（`report.json`）

| 指标 | 值 |
|---|---|
| 验证集准确率 | ~90%（val_acc 0.9054） |
| know / drop F1 | ~0.91 |
| fun F1 | ~0.58（fun 稀缺+边界模糊，接受） |

### 4.5 输出预算（2.21.0 修正）

| 常量 | 值 | 说明 |
|---|---|---|
| `KNOW_BUDGET` | 120 字 | 【要点】总预算 |
| `FUN_BUDGET` | 40 字 | 【趣闻】总预算 |
| `MIN_PIECE` | 12 字 | 单条低于此长度不值得占篇幅 |
| `SIM_RATIO` | 0.7 | 与已选句的字符 Jaccard 超此值视为重复，跳过 |
| `MAX_TOTAL` | 172 字 | **单块**硬上限，不超过 L3 原文兜底的单页上限（`wiki_kb._SNIPPET_LEN` = 180） |
| `config.GAME_WIKI_MAX_CHARS` | 480 字 | **整条 `{wiki}` 注入**的总额上限（多块时生效，由 `processor._clip_knowledge` 把关） |

修掉的三处逻辑缺陷：
1. **超预算的句子**改为「跳过它、给后面的短句机会」——既不整句丢弃导致要点全空
   （旧行为），也不切碎塞进去产生半句话碎片（`refine` 中途的一版）；
   真正「什么都没选上」时由兜底分支保证至少有一条内容，且兜底受长度上限约束
   （旧实现直接塞 `rows[0]` 首句且无约束，实测比 L3 原文还长）。
2. 新增**相似句去重**，消掉「该区域有13张贴纸 / 该区域有12张贴纸」这类模板复读。
3. 截断统一走 `cut_at_boundary()`（优先换行 / 句读 / 空格边界收尾），
   精炼单块与整条注入预算**共用同一份口径**。

实测（模组真会报的实体名）：单块输出 114~162 字，均值 129 字。

### 4.6 多实体分组（2.21.0）

候选行若带 `term`（来自 `wiki_kb.search_candidates(..., per_term=N)`），`refine` 会
**按实体分组**分别选句，每块加 `【实体名】` 前缀：

```
【猪】要点：猪（Pig）是生成于主世界中的常见友好生物。 …  骑乘猪时，只有猪会受到摔落伤害。
【牛】要点：它们是皮革、生牛肉、牛排和奶桶的主要来源。 牛（Cow）是主世界中…
```

不分组会**跨实体混排**——多个实体的句子一起打分排序后，「猪」的段落后面会直接接上
「它们是皮革、生牛肉、牛排和奶桶的主要来源」（那句讲的是牛）。
`search_candidates` 的 `per_term` 同时保证**每个词各取一页**（旧行为整批共享页数上限，
多词查询只覆盖头 1~2 个实体）与**同一页面不被两个词重复取用**（铁镐/钻石镐都指向「镐」页）。

## 五、检索与注入（`curated.py`）

* **精确匹配**（2.21.0 起）：只认 `name` / `id` / 条目可选 `aliases` 的**归一化精确相等**
  * 旧实现是「双向子串 + 字典顺序首命中」，没有对应条目时会拿**包含该词的另一个条目**顶答
    （实测「樱花木」→【樱花木板】、「嗅探兽」→进度【小小嗅探兽】、「木板」→【金合欢木板】），
    等于**注入错误实体的知识**。现在宁可返回 `None` 交给 L2/L3 兜底，也不答错。
  * 同名条目**实体优先**（成就/进度排后），并去掉 `name + id` 完全相同的重复条目 ——
    修掉「同名条目里后一条覆盖前一条、前者永远查不到」。
* **query 感知排序**：query 含「配方/怎么打/耐久/掉落」等 → 对应 facts 前置
* **注入格式**：`【名称】一句话定义 + · 分类事实 + 【趣闻】`，让 AI 区分硬知识与聊资
* `fun` 为空时**不输出**【趣闻】行；当前 1490 条里只有 25 条有内容（见 §八）

```python
from nlu.wiki_refine import curated
curated.prompt(["铁镐"])   # → 【铁镐】铁镐是… · 配方：… · 能力：… · 耐久：…
```

## 六、与桌宠接线（`processor.py`）

```python
def _wiki_knowledge(self, terms):
    engine = self._wiki_engine()          # local / ai / off
    # ① curated 优先
    for t in terms:
        out = wiki_curated.prompt([t])
        parts.append(out) if out else todo.append(t)
    # ② local → 精炼模型；ai → 大 AI 会话；off → 原文
```

| 配置 | 行为 |
|---|---|
| `WIKI_REFINE_ENGINE = "local"`（默认） | curated → 精炼模型 → 原文 |
| `"ai"` | curated → 大 AI 提炼会话 → 原文（旧行为） |
| `"off"` | 完全原文直注入 |
| 旧开关 `ai_wiki_refine=false` | 等价 `off`（向后兼容） |

`wiki_kb.search_candidates()` 新增候选句接口，供精炼模型选句。

## 八、已知限制与后续

1. **`fun`（趣闻）覆盖率极低**：1490 条里只有 **25 条**非空 —— 趣闻只存在于最早那批分片
   （`curated_tools/_mobs/_blocks/_food_mech`），第 2 批 `curated_t2_b1..49`（约 934 条，
   占实体库 3/4）全部没有。这是**内容工作量**（需逐条撰写 + 审核，不适合机械生成），
   所以【趣闻】槽目前基本不生效。**补 fun 是一轮独立的内容任务。**
2. **curated 是静态人工库**：游戏更新（新版本实体）需人工补条；建议用 `wiki_coverage` 审计周期性核对缺口
3. **curated 覆盖率**（对照本地库 common 标题）：612/3539 = 17.3%。注意这个数字被两件事低估：
   ① 分母里仍有约 148 条非实体页（`…定义格式` 系列等）；
   ② 真实入口是**模组报的物品名**（铁镐/钻石剑/樱花木…），这些名字在 `pages` 里根本不是标题
   （只是重定向别名），所以按标题算覆盖率会漏掉 curated 最有价值的那部分条目。
4. **同名（不同 id）条目 37 组**：多为其「FAQ」页与主条目同名；名查询取实体条目，
   其余可按 id 查到。彻底解决需要数据层合并。
5. **精炼模型无 query 理解**：只按「知识价值」选句，针对性弱于大 AI；靠 query 命中小节 + facts 排序缓解
6. **成就/进度中文名**：wiki 成就页大多只有英文 id，129/136 已映射官方译名，7 个新成就保留原 id
7. **复合句/多意图**：精炼模型是分类任务，不处理语义改写（与意图模型一致）
8. `pages_fts`（FTS5 索引）**检索路径未使用**：正文 FTS 兜底曾被刻意禁用
   （正文沾边会把无关页带出，如搜「怪物猎人」命中版本页），暂无启用计划。
9. 后续可：curated 增量脚本（按 wiki 更新自动提示新实体）、成就/进度按版本归类、
   补 fun 内容批次。

> 实测基线与优化记录见 [WIKI_AUDIT.md](../reports/WIKI_AUDIT.md)，复现工具 `tools/wiki_audit.py`。
